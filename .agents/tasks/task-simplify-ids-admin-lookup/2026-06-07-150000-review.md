# Human-friendly counter IDs and admin order lookup

This change replaces Firebase's auto-generated push keys (long random strings like `-NxAbCdEf123`) with short, human-readable counter-based IDs (`ORD-0001`, `PRD-001`, `VPN-0001`, `PXY-0001`) for orders and products. A new admin "Order Lookup" feature lets admins search by these IDs across all three order collections. The approach uses a `counters/` node in Firebase as a poor man's sequence generator: read the current value, increment, write back, and format the result.

**Watch for:** The counter increment is not atomic — two concurrent orders can read the same counter value and produce duplicate IDs (confirmed). The admin lookup handler doesn't sanitize user input before using it as a Firebase path segment (confirmed).

## High-level view

The ID generation function reads a counter, increments it locally, and writes it back as two separate operations with no transactional guarantee. In a single-user Telegram bot with low concurrency this might never collide in practice, but under load (e.g., two users buying at the same instant) the read-then-write pattern can produce duplicate keys, which would silently overwrite one order with the other via `db_set`.

The admin order lookup queries `orders/{id}`, `vpn_orders/{id}`, `proxy_orders/{id}` sequentially until one hits. Since the ID prefix already encodes which collection the order belongs to (`ORD-` → `orders/`, etc.), the code could route on the prefix and skip the redundant lookups.

1. **Race condition in generate_id** — The read-increment-write cycle on `counters/{prefix}` is not atomic. Use Firebase's `transaction()` method to prevent duplicate IDs under concurrent requests.
2. **Path injection in order lookup** — The admin lookup handler passes unsanitized user input directly into a Firebase path (`db_get(f"orders/{oid}")`). Validate that the input matches the expected ID format (`^[A-Z]{2,3}-\d{3,4}$`) before querying.
3. **Redundant lookups despite deterministic prefix** — The lookup always queries all three collections sequentially. Routing on the prefix (`ORD-` → `orders/`, `VPN-` → `vpn_orders/`, `PXY-` → `proxy_orders/`) would reduce Firebase reads from 3 to 1 in the common case.

## Race condition in counter-based ID generation

The `generate_id` function performs a non-atomic read-increment-write:

```python
current = await db_get(f"counters/{prefix}")
new_val = (current or 0) + 1
await db_set(f"counters/{prefix}", new_val)
```

Between the `db_get` and the `db_set`, another concurrent handler (e.g., two users confirming an order at the same moment) can read the same `current` value. Both will compute the same `new_val`, both will write the same counter, and both will get the same ID string back. Because the order is then stored with `db_set(f"orders/{oid}", ...)`, the second write silently overwrites the first order — data loss without any error signal. (confirmed)

Firebase Realtime DB supports `transaction()` on a reference, which performs an optimistic compare-and-swap loop. The fix is straightforward:

```python
ref = fdb.reference(f"counters/{prefix}")
new_val = await _run(ref.transaction, lambda current: (current or 0) + 1)
```

This returns the committed value and retries on conflict. The current implementation works fine for a low-traffic bot where true simultaneous orders are rare, but it's a latent data-loss bug that's trivial to fix now.

## Path injection in admin lookup

The order lookup handler takes raw user text and interpolates it into a Firebase path:

```python
oid = (message.text or "").strip()
order = await db_get(f"orders/{oid}")
```

If an admin types a string containing `/`, the Firebase SDK will interpret it as a deeper path and could read sibling nodes (e.g., typing `ORD-0001/../../users` or just a bare `/`). This is mitigated by the admin-only access gate, but the SDK does accept `/` in the string. A simple regex check (`^[A-Z]{2,4}-\d{3,4}$`) before querying would close this off. (confirmed — no validation exists)

## Prefix-aware routing skipped

Each order ID encodes its collection: `ORD-` → `orders/`, `VPN-` → `vpn_orders/`, `PXY-` → `proxy_orders/`. The lookup handler ignores this and queries all three sequentially until one hits. A lookup for `PXY-0001` always makes two wasted calls first. For a single admin action this is negligible latency, but routing on the prefix would make the code both faster and more self-documenting. (confirmed)
